# Salvor GitHub Pages v1.0.0 Design

## Objective

Build the production GitHub Pages site for Salvor v1.0.0 as a clean, fast,
maintainable static site on `ghpages/v1.0.0`. The page combines the approved
responsive burn-reveal hero, the approved long-form information hierarchy, and
the final V10 node-sigil identity without carrying prototype structure into the
production implementation.

This is a greenfield implementation. Existing prototype files are reference
material for behavior and appearance, not production code to concatenate.

## Quality Bar

Quality, maintainability, accessibility, and measured performance take priority
over delivery speed. The code should be comfortable to show to experienced
frontend engineers reviewing the Salvor repository.

- No runtime framework or third-party JavaScript.
- No external font, icon, or analytics requests.
- Semantic HTML works before JavaScript runs.
- Progressive enhancement owns the burn Easter egg and clipboard convenience.
- Source files have focused responsibilities and avoid duplicated maintained copy.
- Responsive behavior is verified in real browsers, not inferred from CSS alone.
- Small refinements after DOM conversion are allowed within the locked visual
  system and content hierarchy.

## Audience and Page Job

The audience is developers and engineering teams evaluating whether Salvor is a
credible, practical, vendor-neutral memory layer for their repositories. The
page's single job is to explain the value in under a minute and move the visitor
to the v1.0.0 `SETUP_PROMPT.md` or repository.

## Visual System

The design remains the approved terminal/editorial hybrid:

- `paper`: `#ffffff`
- `paper-warm`: `#f8f7f2`
- `ink`: `#050608`
- `ink-soft`: `#4f5154`
- `line`: `#d8d6cf`
- `gold`: `#c9841d`
- `terminal`: `#05090b`
- `terminal-text`: `#f3f0e8`

Typography uses a dependency-free monospace stack based on SF Mono, IBM Plex
Mono when locally available, Roboto Mono when locally available, and platform
monospace fallbacks. The oversized `SALVOR` display, compact utility labels,
hairline rules, three numbered reasons, and dark terminal cards provide the
locked hierarchy. No new decorative visual system is introduced.

The single signature interaction is the hero's wireframe-to-mystic burn reveal.
All other motion remains restrained.

## Page Structure

1. **Hero (`#top`)**
   - Final V10 node sigil and `SALVOR` wordmark.
   - Navigation: `WHY`, `USE`, `CLAUDE`, `GITHUB`.
   - `SALVOR v1.0.0`, `SALVOR`, and `Your repo remembers.`
   - Three accurate bullets: version-controlled agent memory, prompt-first and
     vendor-neutral, and Claude plugin convenience arriving in v1.1.0+.
   - Primary action copies the immutable v1.0.0 `SETUP_PROMPT.md` when the
     Clipboard API and network request succeed, with the tagged GitHub file as
     its normal anchor fallback. The secondary action opens the repository.
   - Initial state uses the approved `04 bold aligned eye` wireframe.
   - Background click or drag ignites the approved self-sustaining zipper/ember
     burn that reveals the aligned mystic image. The interaction remains an
     undisclosed Easter egg with a normal cursor.

2. **Three reasons (`#why`)**
   - The repo remembers why.
   - Every agent reads the same truth.
   - No SaaS, no lock-in.

3. **How Salvor works**
   - Hub and spoke.
   - Two-tier memory.
   - Three capture triggers.
   - Versioned why.
   - Serena and GitNexus.

4. **Use Salvor (`#use`)**
   - Two dark, rounded terminal cards inside the light page.
   - The vendor-neutral prompt path is marked as the v1.0.0 primary path and
     contains installation steps and a concise command example.
   - The Claude card is explicitly marked as a v1.1.0+ future convenience. It
     must not imply that the plugin or its commands ship in v1.0.0.
   - `#claude` points to the future-facing Claude card.

5. **Built on open foundations**
   - Serena: semantic code intelligence.
   - GitNexus: code graph and impact analysis.
   - Links go to their official repositories.

6. **Closing line and footer**
   - `Salvage your knowledge before it's lost to the next session.`
   - V10 white mark, open-source/MIT context, v1.0.0, GitHub, docs, and
     `SETUP_PROMPT.md` links.

On tablet and phone, the content becomes a single readable column, the five-step
flow becomes a scrollable or stacked sequence without clipped text, the dark
cards stack, and a compact real menu preserves all navigation targets.

## Production Architecture

### `site/index.html`

Contains the semantic page, metadata, one canonical copy of hero text, inline
decorative SVG icons, and accessible link/button labels. The page remains useful
if JavaScript fails or is disabled.

### `site/styles.css`

Contains tokens, layout, component styles, responsive rules, focus states,
selection treatment, and reduced-motion rules. Selector specificity stays
shallow and class-based. Breakpoints are driven by layout failure points rather
than device labels.

### `site/scripts/site.js`

Owns the mobile menu, copy-to-clipboard enhancement, link-safe event handling,
and small interface state. Clipboard failure leaves the canonical link usable
and returns the control label to its default state. The prompt is fetched from
the immutable `v1.0.0` raw GitHub URL so the Pages payload does not duplicate the
release's canonical installer.

### `site/scripts/burn-reveal.js`

Owns only the canvas burn field, masks, ember edge, image registration, pointer
ignition, resize handling, and cleanup. It derives visual burn layers from the
single semantic hero source at runtime so the maintained HTML does not contain
three manually synchronized copies of the content. Visual clones are
`aria-hidden` and pointer-inert; the canonical foreground content remains
selectable and interactive before, during, and after the burn.

The burn module initializes only after the wireframe is drawable. It pauses when
the page is hidden, respects reduced-motion preferences, and avoids starting on
links or text-selection gestures. A single ignition remains self-sustaining;
multiple clicks and drag paths merge into the same field.

### Assets

Production assets live under `site/assets/` so the README and deployed site can
use one committed source:

- V10 node-sigil black and white SVG masters.
- V10 transparent PNGs at 128, 64, 48, 32, and 16 pixels.
- The approved wireframe hero.
- Optimized mystic hero formats with an appropriate fallback.
- A static social preview using the V10 identity and v1.0.0 messaging.

V8 exports, exploratory contact sheets, logo-generation Python, and obsolete
hero prototypes are excluded from the production Pages payload. The repository
may retain approved historical design artifacts only when they serve an explicit
documentation purpose; they are not loaded by the site.

## Performance Strategy

- Keep the first-view HTML/CSS/JS dependency-free and cacheable.
- Use responsive AVIF/WebP mystic imagery with a reliable fallback.
- Preserve the 1:1 wireframe/mystic registration across formats and viewports.
- Give the visible wireframe priority; decode the mystic image without blocking
  semantic content rendering.
- Use SVG for displayed brand marks and inline section icons; PNG favicon sizes
  are chosen explicitly rather than browser-scaled from a large bitmap.
- Defer non-critical scripts and initialize the burn module after DOM parsing.
- Avoid layout shifts by declaring image dimensions/aspect ratios.
- Establish a measured local target: no horizontal overflow or console errors,
  stable hero geometry, and a strong Lighthouse performance/accessibility result
  without compromising the approved interaction.

## Accessibility and Progressive Enhancement

- One logical heading hierarchy and descriptive landmarks.
- Keyboard-visible focus on every actionable element.
- Real anchors for navigation and outbound actions.
- The menu exposes accurate `aria-expanded` state and closes on selection,
  Escape, and outside interaction.
- Hero text is normal selectable text at every burn state.
- Decorative images/canvases are hidden from assistive technology.
- The burn effect never steals link activation or an intentional text selection.
- `prefers-reduced-motion` keeps a static wireframe hero and disables the burn
  animation unless a later explicit control is added.
- High-contrast wireframe and mystic states remain readable independently.

## Version Accuracy

The supplied `salvor-v1.0.0.zip`, especially its README and CHANGELOG, is the
content authority. The page must not present the Claude Code plugin as released.
The vendor-neutral prompt is the only available installation path in v1.0.0.

Repository links may point at the immutable `v1.0.0` tag where the visitor needs
release-specific content; general project and community links may point at the
repository root.

## README and Deployment

The README badge/logo is replaced with the V10 node sigil. References use the
committed production logo asset; no generator is needed to render the README.

The GitHub Pages workflow deploys only `site/` when `ghpages/v1.0.0` is pushed or
when the workflow is manually dispatched. The implementation must not assume
files above `site/` are available at runtime. The later v1.1.0 integration will
deliberately update the publishing branch rather than coupling this page to
`main` prematurely.

## Analytics Decision

Do not add Google Analytics to v1.0.0. GA is technically normal and possible on
a static GitHub Pages site, but it adds a third-party request and privacy/consent
work that does not improve the initial product experience. Use GitHub's built-in
repository traffic, referrer, popular-content, and clone reporting for launch.
Add page analytics later only through a separate, explicit decision that compares
privacy, consent, performance, and the exact questions the data must answer.

## Verification

Automated checks are written before production behavior and cover:

- required v1.0.0 copy and absence of released-plugin claims;
- navigation targets, external link destinations, metadata, and V10 assets;
- semantic structure, reduced-motion styling, and JavaScript syntax;
- no missing local resources.

Real-browser verification uses Playwright against a local HTTP server at minimum:

- desktop: 1440 x 1000;
- tablet: 768 x 1024;
- small phone: 390 x 844;
- narrow phone stress case: 320 x 568.

The browser pass covers initial wireframe rendering, partial and completed burn,
wireframe/mystic registration, text selection at all burn states, mobile menu,
keyboard focus, clipboard feedback, internal/outbound links, reduced motion,
horizontal overflow, layout shifts, failed requests, and console/page errors.
Screenshots are captured for desktop, tablet, and small-phone review.

## Out of Scope

- The v1.1.0 page and released-plugin wording.
- Google Analytics or another analytics provider.
- A framework, bundler, CMS, or server component.
- Redesigning the approved visual hierarchy.
- Reworking the V10 logo geometry.
